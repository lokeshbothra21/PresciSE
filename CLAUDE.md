## Project Overview

**PresciSE** is a Retrieval-Augmented Generation (RAG) system for answering scientific questions from PDFs using hybrid search (BM25 + FAISS) and LLM-powered synthesis via a DD+Expert iterative multi-agent LangGraph loop.

## Setup

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env  # Add GEMINI_API_KEY
```

Requires Python 3.10+, 4GB+ RAM, and a Gemini API key.

## Running

```bash
# Quick query runner — shows router decision, top hits, then the answer
python -m scripts.ask "Your question here?"
python -m scripts.ask "Your question here?" --top-k 5
python -m scripts.ask "Your question here?" --rebuild   # force re-index first

# Full demo (indexes PDFs in data/pdfs/, then answers a default question)
python -m scripts.pdf_demo
python -m scripts.pdf_demo "Your question here?"
python -m scripts.pdf_demo --clean   # suppress debug logs

# FastAPI web server (api/ + frontend/)
uvicorn api.main:app --reload
```

There is no formal test suite or lint configuration. Diagnostic/test scripts live in `scripts/`.

## Architecture

The system operates in two phases on each query:

**Phase 1A — Indexing (one-time, offline):** PDFs in `data/pdfs/` are parsed by Docling, chunked into 900-char segments with 150-char overlap, enriched with TF-IDF keywords and spaCy NER, embedded using SPECTER (768-dim), and indexed into BM25 + FAISS. Mathematical formulas get a separate extraction/indexing pipeline — each formula chunk stores both a normalised ASCII-math form and a renderable `latex_formula` string produced by `ascii_math_to_latex()`. All indexes are persisted to `data/index/` using SHA256 change detection to avoid re-indexing unchanged documents.

**Phase 1B — Retrieval (online, per query):** The query is embedded and routed through a local Qwen2.5-1.5B model that dynamically weights BM25 vs. FAISS based on query intent. The `DDExpertAgent` handles its own per-subquestion retrieval internally by calling `retriever.retrieve_with_formulas()` for each subquestion generated by the DD planning step.

**Phase 2 — Answer Generation (DD+Expert LangGraph loop):** `DDExpertAgent` (`core/agent/dd_expert_agent.py`) runs an iterative `StateGraph`:

```
dd_plan → retrieve → expert_answer → dd_evaluate
                          ↑                  │ (not satisfied & iter < 4)
                          └──────────────────┘
                                             │ (satisfied or iter ≥ 4)
                                             ▼
                                         synthesize → END
```

- **dd_plan**: DD reads corpus context, generates 3–6 subquestions, or returns an out-of-scope signal.
- **retrieve**: Embeds + retrieves top-k chunks per subquestion.
- **expert_answer**: Single batched LLM call — Expert answers all subquestions with citations.
- **dd_evaluate**: DD judges whether evidence is sufficient; if not, refines 1–3 subquestions and iterates.
- **synthesize**: DD writes the final grounded answer from all accumulated Q&A pairs.

Max LLM call budget: 1 (plan) + 4 × 2 (expert + evaluate) + 1 (synthesize) = **11 calls**.

## Key Design Rules

- **All business logic belongs in `core/`**. Scripts in `scripts/` are strictly for orchestration, demos, and diagnostics.
- New features must be implemented in the appropriate `core/` submodule, then called from scripts.
- The entry point for index orchestration is `core/persistence/index_manager.py`.
- The primary LangGraph agent entry point is `core/agent/dd_expert_agent.py`.
- `DDExpertAgent` requires three runtime dependencies: `retriever` (HybridRetriever), `embedder` (Embedder), and `llm` (GeminiClient), plus a `context_description` string from `build_context_description(retriever.chunks)`.

## Formula Pipeline

### Storage format

Each `FormulaChunk` stores:
- `formula_text` — raw text as extracted from PDF
- `normalized_formula` — cleaned ASCII-math (e.g. `E = mc^2`)
- `latex_formula` — renderable LaTeX (e.g. `E = mc^{2}`) produced by `ascii_math_to_latex()`

`_build_display_text()` emits `[FORMULA]$latex$[/FORMULA]` when `latex_formula` is non-empty, which propagates into evidence blocks and LLM prompts.

### Formula notation in prompts / answers

LLM prompts instruct the model to reproduce formulas as `[FORMULA]$exact LaTeX$[/FORMULA]` on their own line. `render_formula_answer()` in `output_formatter.py` passes `$...$` blocks through unchanged (for KaTeX rendering in the browser) and applies legacy Greek→Unicode conversion only to non-LaTeX blocks.

### Env vars (default off in `scripts/ask.py`)

```
PRESCISE_ENABLE_FORMULA_ENRICHMENT=1   # extract/index mathematical formulas
PRESCISE_ENABLE_CODE_ENRICHMENT=1      # extract/index code blocks
PRESCISE_ENABLE_VLM_FALLBACK=1         # use VLM (vision) fallback for hard PDFs
PRESCISE_FORMULA_QUALITY_MODE=balanced # balanced | fast | accurate
```

## Configuration

`config/retrieval_config.yaml` controls retrieval weights (default: BM25 0.6, FAISS 0.4), top-k values, the router model (`Qwen/Qwen2.5-1.5B-Instruct`), and formula search settings. The Qwen router adjusts these weights dynamically at runtime based on query intent.

`config/app_config.yaml` controls logging level, environment, and external LLM access settings.

## Logging

Uses `loguru`. Set log level in `config/app_config.yaml`. See `HOW_TO_CHECK_LOGS.md` for details on reading formula diagnostics and controlling verbosity.
